拡張機能は独自のインデックス構造を登録し、サーバーからそれを呼び出させることができます。サーバーは SQL 構文、メタデータ、およびトランザクションを所有します。拡張機能はインデックスのディスク上のフォーマットと、その中の検索を所有します。

これを担うプレビュー機能は2つあります。`vsql::preview::index_type` はインデックス構造そのものを登録します。`vsql::preview::index_profile` はその構造をカスタムタイプに結び付け、インデックスが計算に使用する関数を指定します。どちらも `<villagesql/preview/index_builder.h>` にあります。

<Warning>
カスタムインデックスの SQL は実装されていません。カスタムインデックスを指定するステートメントは、すべてのビルドで `ERROR 3219 (HY000): Extended Index feature not yet implemented` を返します。

実装済みで、[SQL 構文](#the-sql-syntax)で説明するテストフラグを介して MTR スイートからのみ到達可能なもの：両方の機能、このページのビルダー API、および DDL パスです。インデックスの作成は拡張機能の `create` フックを呼び出し、サーバーのメタデータにそのインデックスを記録します。削除は `drop` を呼び出します。メタデータは再起動後も維持されます。

未実装のもの：`INSERT`、`UPDATE`、`DELETE` におけるインデックスの保守と、カスタムインデックスを介したクエリの実行です。DML およびスキャンのフックは呼び出されません。
</Warning>

## 3つの構成要素 {#the-three-pieces}

インデックスタイプは構造です。エントリをどのように格納し、挿入し、削除し、スキャンするかを定めます。これは `hnsw` のような名前で、拡張機能ごと・構造ごとに1回登録されます。

インデックス関数は、プロファイルに結び付けられた決定論的な関数です — たとえば距離関数です。プロファイルは2種類を結び付けます。`with_function()` で結び付けられた関数は SQL 上でユーザーに見え、オプティマイザはその呼び出しに対してインデックススキャンを計画する場合があります。`with_helper()` で結び付けられた関数は、インデックスの実装からのみ呼び出されます。

インデックスプロファイルは、カスタムタイプをインデックスタイプに結び付け、結び付けられた各関数にインデックスが呼び出しに使用する数値 ID を与えます。1つのインデックスタイプは多数のプロファイルに対応します。`vsql_vector` は単一の `hnsw` インデックスタイプと、その上に4つのプロファイル — `hnsw_l1`、`hnsw_l2`、`hnsw_cosine`、`hnsw_inner_product` — を距離メトリックごとに1つずつ登録します。

## インデックスタイプの登録 {#registering-an-index-type}

`make_index_type<Name, Context>()` は、インデックス名と、拡張機能が必要とする実行時の状態を保持するインデックスごとのコンテキスト構造体を取ります。12個のフックはすべて必須で、3つのグループに分かれます。1つでも欠けているとビルダーはコンパイルされません — 失敗したアサーションがそのフックの名前を示します。

ライフサイクルフックは、インデックスストレージを作成し、テーブルが開かれるときにロードし、削除します：

```cpp
bool create(Ctx *, const Index &, Space::Ref, Segment::TrxRef, char *, uint32_t);
bool load(Ctx *, const Index &, Index::StorageRef, char *, uint32_t);
bool drop(Ctx *, const Index &, Segment::TrxRef, char *, uint32_t);
```

DML フックは、行の変更に応じてインデックスを保守します。削除は2段階です。`mark_delete` はエントリに削除マークを付け、`delete_mark` 引数が false の場合はマークを外します。`purge` はエントリを完全に削除します：

```cpp
bool insert(Ctx *, const Index &, Segment::TrxRef,
            IndexScanKey::KeyPartData *keys, IndexScanKey::KeyPartData *pkeys,
            IndexScanKey::KeyPartRef *key_ref, char *, uint32_t);
bool mark_delete(Ctx *, const Index &, Segment::TrxRef,
                 IndexScanKey::KeyPartRef *key_ref,
                 IndexScanKey::KeyPartData *keys,
                 IndexScanKey::KeyPartData *pkeys, bool delete_mark,
                 char *, uint32_t);
bool purge(Ctx *, const Index &, Segment::TrxRef,
           IndexScanKey::KeyPartRef *key_ref, IndexScanKey::KeyPartData *keys,
           IndexScanKey::KeyPartData *pkeys, char *, uint32_t);
```

スキャンフックはクエリに応答します。`save` と `restore` はミニトランザクションの境界を挟みます。サーバーは、カーソルが接続されているミニトランザクションをコミットしようとするときに `save` を呼び出し、新しいミニトランザクションを開始した後に `restore` を呼び出します。ミニトランザクションのコミットはページラッチを解放するため、`save` は位置を再び見つけるのに十分な論理的状態を記録し、`restore` はスキャンが必要とするラッチを再取得します：

```cpp
bool begin(Ctx *, const Index &, MtrCtx::Ref, const IndexScanDesc &,
           Index::Cursor *, bool *, char *, uint32_t);
bool position(Index::Cursor, Index::CursorOp, bool *, char *, uint32_t);
bool fetch(Index::Cursor, IndexScanKey::KeyPartRef *,
           IndexScanKey::KeyPartData *keys, IndexScanKey::KeyPartData *pkeys,
           char *, uint32_t);
bool save(Index::Cursor, char *, uint32_t);
bool restore(Index::Cursor, MtrCtx::Ref, bool *, char *, uint32_t);
void end(Index::Cursor *);
```

失敗しうるすべてのフックは、最後の2つの引数としてメッセージバッファとその長さを取り、そこにメッセージを書き込んだ上で失敗時に `true` を返します。

カーソルは拡張機能に属します。`begin` でカーソルを割り当てて `*cursor` に代入し、`end` で解放して `*cursor` を `nullptr` に設定してください。C++ SDK はカーソルの状態をラップしません。

コンテキストは拡張機能に属しません。C++ SDK は `create` または `load` を呼び出す前に、InnoDB のアリーナから `Index::StorageCtx<T>` とあなたの `T` を割り当て、`drop` が返った後にアリーナを破棄します — これにより `~T` が実行されます。自身の状態には `ctx->user()` を通じて、アリーナには `ctx->arena()` を通じてアクセスしてください。コンテキスト、ユーザーオブジェクト、アリーナを削除してはいけません。

### インデックスができることの宣言 {#declaring-what-the-index-can-do}

`.capabilities()` は、インデックスがサポートするアクセスパターンを宣言します。少なくとも1つの値が必要です。`|` で組み合わせてください：

| 値 | 意味 |
|---|---|
| `Index::Support::POINT_LOOKUP` | 完全なキー値による完全一致のルックアップ |
| `Index::Support::RANGE_SCAN` | 開始境界、終了境界、またはその両方を持つ範囲スキャン |
| `Index::Support::REVERSE_SCAN` | キーの降順でのスキャン |
| `Index::Support::ORDER_BY` | スキャンがキー順に行を返すため、オプティマイザはソートなしでインデックスカラムに対する `ORDER BY` を満たせます |
| `Index::Support::KNN` | `ORDER BY <distance>(<column>, <reference>) LIMIT K` のための K 近傍スキャン |

`.storage_props()` は、各インデックスエントリがインデックス対象のデータをどのように参照するかを宣言します。InnoDB がこれを使用し、`HAS_ROW_REF` または `HAS_COLUMN_REF` の少なくとも一方を設定する必要があります。どちらを提供するかは、インデックス作成時にサーバーが選択します：

| 値 | 意味 |
|---|---|
| `Index::Storage::HAS_ROW_REF` | エントリはインデックス対象の行のプライマリキーを格納し、サーバーはプライマリキーのルックアップでヒットを解決します |
| `Index::Storage::HAS_COLUMN_REF` | エントリはサーバーが提供する安定したカラム参照を格納します。これはベクトルのカラムストレージのように、カラムが安定した物理アドレスを持つ場合に利用できます。プライマリキー全体を格納することを回避します |
| `Index::Storage::REF_LOOKUP` | インデックスは安定した参照トークンからエントリを再特定できます。これは、インデックスがポイントルックアップを持たない場合に、パージなどの内部操作が使用します |

`REF_LOOKUP` の宣言には義務が伴います。パージがまだ削除していないすべてのエントリは、一意の参照トークンを持たなければならず、削除マークが付いているだけのエントリもこれに含まれます。拡張機能はこれを保証する必要があります。

### インデックスオプション {#index-options}

DDL 内の `WITH (M = 8, ef_construction = 64)` は、インデックスオプションとして拡張機能に届きます。サーバーはすべてのキーと値を先に小文字化するため、DDL では `M` と書かれていても `params[i].key` は `m` と読み取れます。デフォルト値と `parse` 関数を持つ構造体を宣言し、`.options<T, &T::parse>()` で登録してください：

```cpp
struct HNSWOptions {
  int M = 16;
  int ef_construction = 200;
  static bool parse(const Index::Parameter *params, uint32_t count,
                    HNSWOptions *out, char *error_msg,
                    uint32_t error_msg_len);
};
```

小文字化されたキーと比較します：

```cpp
if (strcmp(params[i].key, "m") == 0) out->M = atoi(params[i].value);
```

`index.options<HNSWOptions>()` は、パースされた構造体へのポインタを返します。これは `Index` を受け取るすべてのフック — ライフサイクルフック、DML フック、および `begin` — から到達可能です。残りのスキャンフックはカーソルのみを受け取るため、スキャンの途中でオプションを必要とするインデックスタイプは、`begin` でそれらをカーソルにコピーする必要があります。

## インデックス関数 {#index-functions}

インデックス関数は決定論的でなければなりません。関数を構築し、`static const` で保持してください — プロファイルはその参照を格納するため、そのアドレスは登録より長く存続する必要があります：

```cpp
static const auto MY_INDEX_FN =
    make_index_function<&my_index_fn>("my_index_fn")
        .returns(vsql::REAL)
        .param(MY_TYPE)
        .param(MY_TYPE)
        .deterministic()
        .build();
```

## インデックスプロファイル {#index-profiles}

プロファイルは、カスタムタイプ、インデックスタイプ、および ID 付きの関数を指定します。`for_type()` はタイプの*名前文字列* — `make_type` に渡すのと同じ定数 — を取り、タイプディスクリプタは取りません。`with_function()` と `with_helper()` は、名前ではなく構築済みのインデックス関数を取ります：

```cpp
static const auto MY_PROFILE =
    make_index_profile("my_profile")
        .for_type(kMyType)
        .using_index(kMyIndex)
        .with_function(1, MY_DISTANCE_FN)
        .with_helper(1, MY_HELPER_FN)
        .ordering(Index::Ordering::ASC)
        .default_for_type(true)
        .build();
```

ID は各リスト内で一意でなければならず、2つのリストは独立して番号付けされます — `with_function(1, ...)` と `with_helper(1, ...)` は衝突しません。1つのリスト内で ID が重複した場合、`INSTALL EXTENSION` で拒否されます。

フックからは `index.profile()` および `index.helper()` を通じて呼び出します：

```cpp
template <typename Result, typename... ColData>
void profile(uint32_t key_pos, uint32_t fn_id, Result *result,
             const ColData &...args) const;

template <typename Result, typename... ColData>
void helper(uint32_t key_pos, uint32_t fn_id, Result *result,
            const ColData &...args) const;
```

`key_pos` は、結び付けられたプロファイルが `fn_id` をディスパッチする、ゼロ始まりのキーカラムです。1つのプロファイルは1つのキーカラムに結び付くため、複数のカラムにまたがるインデックスは、各位置を通じて異なるプロファイルに到達できます。`args` のすべての値は、カラムの値を永続化された形式で運ぶ `vef_storage_col_data_t` でなければなりません。それ以外のタイプは、コンパイル時に `static_assert` が拒否します。

`.ordering()` は `NONE`、`ASC`、`DESC`、またはプロファイルが両方のスキャン方向をサポートする場合は `ASC | DESC` を取ります。値が大きいほど類似度が高いことを意味する距離メトリックは `DESC` であり、`vsql_vector` は `hnsw_inner_product` をこのように登録しています。

`.default_for_type(true)` は、ステートメントがプロファイルを指定しない場合に使用するプロファイルとして、このプロファイルをマークします。これはタイプとインデックスタイプの組み合わせごとに適用され、デフォルトは false です。`vsql_vector` は `hnsw_l2` をマークしており、そのためプロファイルを指定せずに作成されたインデックスは `hnsw_l2` を記録します。

関数またはヘルパーは `REAL` を返さなければなりません。他の戻り値のタイプはまだサポートされていません。そのシグネチャで宣言できるパラメータは最大8個で、これは `VEF_INDEX_PROFILE_FN_MAX_ARGS` の値です。サーバーはこの両方を、最初の使用時ではなく `INSTALL EXTENSION` で検査します。

## 組み合わせる {#putting-it-together}

```cpp
#include <villagesql/preview/index_builder.h>
#include <villagesql/vsql.h>

using namespace vsql::preview_index_builder;

static constexpr const char kMyType[] = "my_type";
static constexpr const char kMyIndex[] = "my_index";

constexpr auto MY_TYPE = vsql::make_type<kMyType>()/* ... */.build();

static constexpr auto MY_INDEX =
    make_index_type<kMyIndex, MyContext>()
        .lifecycle()
            .create<&my_create>()
            .load<&my_load>()
            .drop<&my_drop>()
        .dml()
            .insert<&my_insert>()
            .mark_delete<&my_mark_delete>()
            .purge<&my_purge>()
        .scan()
            .begin<&my_begin_scan>()
            .position<&my_position>()
            .fetch<&my_fetch>()
            .save<&my_save>()
            .restore<&my_restore>()
            .end<&my_end_scan>()
        .global()
            .capabilities(Index::Support::KNN)
            .storage_props(Index::Storage::HAS_COLUMN_REF |
                           Index::Storage::REF_LOOKUP)
            .options<MyOptions, &MyOptions::parse>()
            .build();

static const auto MY_PROFILE =
    make_index_profile("my_profile")
        .for_type(kMyType)
        .using_index(kMyIndex)
        .with_function(1, MY_INDEX_FN)
        .ordering(Index::Ordering::ASC)
        .default_for_type(true)
        .build();

static auto INDEX_TYPE = IndexTypeCapability().index_type(MY_INDEX);
static auto INDEX_PROFILE = IndexProfileCapability().index_profile(MY_PROFILE);

VEF_GENERATE_ENTRY_POINTS(
    vsql::make_extension()
        .with(INDEX_TYPE)
        .with(INDEX_PROFILE)
        .type(MY_TYPE))
```

どちらの機能オブジェクトも `static` でなければならず — C++ SDK はその中へのポインタを保持します — それぞれを `.with()` に正確に1回渡す必要があります。1つの機能オブジェクトは複数の構造を運べます。構造ごとに `.index_type()` または `.index_profile()` をチェーンしてください。

同じインデックスタイプ名を2回、または同じプロファイル名を2回登録することは、インストール時に拒否されます：

```text
ERROR HY000: Failed to install extension 'dup_index_type': index type 'DUP_INDEX' already exists
ERROR HY000: Failed to install extension 'dup_index_profile': index profile 'DUP_PROFILE' already exists
```

## SQL 構文 {#the-sql-syntax}

カスタムインデックスは `USING EXTENDED` で選択し、カラムは使用するプロファイルを指定できます：

```
INDEX <name> (<column> [[<extension>.]<profile>] [ASC | DESC])
  USING EXTENDED([<extension>.]<index_type>)
  [WITH (<option> = <value>[, ...])]
```

この句は `CREATE TABLE` 内のインラインで機能し、`CREATE INDEX` および `ALTER TABLE ADD INDEX` でも機能します。プロファイルとインデックスタイプはどちらも拡張機能名で修飾でき、これにより同じ名前を提供する2つの拡張機能を区別できます。プロファイルが指定されていない場合、サーバーはそのタイプとインデックスタイプに対して `default_for_type(true)` を宣言したプロファイルを使用します。

例として `vsql_vector` を使用します：

```sql
CREATE TABLE t1 (
  id INT PRIMARY KEY,
  a SVECTOR(4) NOT NULL,
  b SVECTOR(8) NOT NULL,
  INDEX idx_a (a) USING EXTENDED(hnsw),
  INDEX idx_b (b hnsw_cosine) USING EXTENDED(hnsw) WITH (M = 8, ef_construction = 64)
) ENGINE=InnoDB;

CREATE INDEX idx_c ON t1 (a hnsw_l1) USING EXTENDED(hnsw);

ALTER TABLE t1 ADD INDEX idx_d (b vsql_vector.hnsw_inner_product)
  USING EXTENDED(vsql_vector.hnsw);
```

削除は通常どおりです。`DROP INDEX`、`ALTER TABLE ... DROP INDEX`、または `DROP TABLE` を使用します。`DROP TABLE` はテーブルとともにインデックスのメタデータを削除します。

このセクションのすべてのステートメントは `ERROR 3219 (HY000): Extended Index feature not yet implemented` を返します。

デバッグビルドでは、セッションがガードをバイパスするテストフラグを設定した場合、これらのステートメントを受け付けます：

```sql
SET SESSION debug='+d,villagesql_custom_index_proceed';
```

カスタムインデックスの MTR スイートはこのフラグを使用します。これは DDL パスのみを実行します。DML およびスキャンのフックは依然として呼び出されないため、行がインデックスに届くことはなく、クエリがそこから読み取ることもありません。

<Note>
`SHOW CREATE TABLE` は現在、カスタムインデックスを単なる `KEY` 句として表示します。インデックスタイプ、プロファイル、および `WITH` パラメータは表示されないため、その出力はそれを作成したステートメントに戻すことができません。
</Note>

## メタデータの保存場所 {#where-the-metadata-lives}

サーバーは各カスタムインデックスを `villagesql.custom_indexes` に記録し、そのキーカラム — 各カラムに結び付けられたプロファイルとともに — を `villagesql.custom_index_columns` に記録します。どちらも再起動後も維持されます。

どちらも `root` を含めて SQL からは読み取れません：

```sql
SELECT * FROM villagesql.custom_indexes;
```

```
ERROR 3554 (HY000): Access to table 'villagesql.custom_indexes' is rejected.
```

これらはサーバー内部のものとして扱ってください。クライアントからカスタムインデックスのメタデータを調べる、サポートされた方法はまだありません。
