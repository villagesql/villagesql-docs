只读副本是第二台服务器，它重放源服务器写入的所有内容，并响应读取查询。副本几乎可以线性地扩展读取能力，并为故障转移提供一份温备副本，代价是您的应用必须承担一个新问题：副本总是稍微滞后，而且没有任何配置选项能消除这一点。复制本身的搭建在[复制基础](/zh/guides/replication-basics)中介绍；本指南讲的是如何用好副本。

## 副本的用途 {#what-replicas-are-for}

- **读取扩展。** 仪表盘、搜索、导出和 API 读取都从源服务器移走，为写入保留其容量。
- **隔离昂贵的查询。** 分析师那条 40 秒的聚合查询在副本上运行，不会阻塞任何人。
- **温备机。** 当源服务器故障时，可以提升一个数据最新的副本。

副本不是什么：它不是写入扩展工具。每个副本都会重放源服务器接受的每一次写入，所以副本不会增加任何写入容量。

## 路由读取 {#routing-reads}

MySQL 不会替您路由查询。您的技术栈中必须有某个组件把写入发送到源服务器，把选定的读取发送到副本：

- **应用级路由。** 大多数框架直接支持（Django 数据库路由器、Rails 的 `connects_to`/角色、Laravel 的读/写连接）。简单且显式；由应用逐条查询决定。
- **代理。** ProxySQL 之类的代理按语句类型或规则路由，这样应用只需保留一个连接字符串。这也把故障转移集中到了一处。

从应用级路由开始。它会迫使您尽早提出正确的问题：不是"这条查询能否在副本上运行"，而是"这条查询能否容忍过期数据"。

## 复制延迟：真正的难点 {#replication-lag-the-actual-hard-part}

复制默认是异步的。源服务器上的提交会在副本应用该变更之前就返回，所以片刻之后在副本上的读取可能看不到一次已经成功的写入。在副本上测量延迟：

```sql
SHOW REPLICA STATUS\G
```

`Seconds_Behind_Source` 字段是标准信号。它通常接近零，并在写入突发、大事务和模式变更时飙升。对它设置告警，并了解每条读取路径的容忍度。

经典的故障是**读己之写**：用户保存了个人资料（写入源服务器），下一个页面从副本加载它，而副本尚未应用这次写入。用户看到自己的修改消失了。标准的缓解措施，按成本从低到高：

- **写后固定。** 会话写入之后，在接下来的几秒内把该会话的读取路由到源服务器。许多框架和代理直接支持这种模式。
- **按容忍度路由。** 账户余额和刚编辑过的页面从源服务器读取；浏览页面、搜索和分析从副本读取。
- **通过 GTID 实现会话一致性。** 写入之后，捕获事务标识符，并让副本上的读取使用 `WAIT_FOR_EXECUTED_GTID_SET()` 等待它。精确，但代价是要把 GTID 贯穿整个请求。

## 两条实用规则 {#two-practical-rules}

- **副本的硬件配置应当不低于源服务器，而不是用剩下的旧机器。** 比源服务器慢的副本，恰恰会在促使您添加副本的那种负载下落后。
- **演练提升。** 一个您从未提升过的副本，就像一份您从未恢复过的备份。在需要之前先练习故障转移路径。

VillageSQL 从 MySQL 8.4 原样继承了这套复制机制，所以上面的一切同样适用于它。
