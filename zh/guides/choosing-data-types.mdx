您为列指定的数据类型影响存储大小、索引效率和查询行为。选择比必要更大的类型会在每一行以及包含该列的每个索引中浪费空间。选择太小的类型会导致截断错误或静默的数据丢失。

## 整数类型 {#integer-types}

MySQL 有五种整数类型。请选择能容纳您预期范围的最小类型。

| 类型 | 存储 | 范围（有符号） | 适用场景 |
|:-----|:--------|:---------------|:---------|
| `TINYINT` | 1 字节 | -128 到 127 | 标志、状态码、小型枚举 |
| `SMALLINT` | 2 字节 | -32,768 到 32,767 | 不会超过约 32K 的计数或 ID |
| `MEDIUMINT` | 3 字节 | -830 万到 830 万 | 中等范围的 ID 或计数器 |
| `INT` | 4 字节 | -21 亿到 21 亿 | 大多数 ID 和计数器 |
| `BIGINT` | 8 字节 | ±920 亿亿 | 大型 ID、毫秒级 Unix 时间戳 |

`INT UNSIGNED` 把正数范围翻倍到约 43 亿。对始终为正的主键和外键使用 `UNSIGNED`——这是免费的额外范围。

`BIGINT` 的存储是 `INT` 的两倍。不要默认对所有 ID 都使用它——`INT` 可以处理超过 20 亿行，这比大多数表能达到的规模都大。

## 字符串类型 {#string-types}

### VARCHAR 与 CHAR {#varchar-vs-char}

`VARCHAR(n)` 只存储字符串实际包含的字节数（加上 1-2 字节的长度）。`CHAR(n)` 始终存储 `n` 个字符，用空格填充较短的字符串：在单字节字符集中为 `n` 个字节，在 `utf8mb4` 中最多为 `4n` 个字节。

| 类型 | 存储 | 适用场景 |
|:-----|:--------|:---------|
| `CHAR(n)` | 始终为 `n` 个字符 | 固定长度的字符串（国家代码、'Y'/'N' 之类的状态标志、MD5 哈希） |
| `VARCHAR(n)` | 实际长度 + 1-2 字节 | 可变长度的字符串（姓名、电子邮件、URL） |

对于固定长度的值，`CHAR` 可能略快，因为不需要解析长度前缀。对于任何可变长度的内容，请使用 `VARCHAR`。

### VARCHAR 与 TEXT {#varchar-vs-text}

```sql
-- VARCHAR stores inline in the row (up to row size limit)
name VARCHAR(255)

-- TEXT stores off-page once it exceeds a threshold; inline storage is limited
description TEXT
```

不超过行大小限制的 `VARCHAR` 值内联存储在聚簇索引页中。`TEXT`（和 `BLOB`）值一旦足够大就存储在溢出页中。这意味着：
- `VARCHAR` 列直接包含在索引中
- `TEXT` 列无法完整建索引——您需要一个前缀长度：`INDEX (description(100))`

对于您知道不超过几百个字符的字符串，使用 `VARCHAR`。对于内联存储没有意义的长内容（文章、评论、HTML），使用 `TEXT`。

## 日期和时间类型 {#date-and-time-types}

| 类型 | 存储 | 范围 | 适用场景 |
|:-----|:--------|:------|:---------|
| `DATE` | 3 字节 | 1000-01-01 到 9999-12-31 | 仅日期，无时间 |
| `TIME` | 3 字节 | -838:59:59 到 838:59:59 | 时长或一天中的时间 |
| `DATETIME` | 5 字节 | 1000-01-01 到 9999-12-31 | 不做时区转换的时间戳 |
| `TIMESTAMP` | 4 字节 | 1970-01-01 到 2038-01-19 | 自动更新的时间戳；以 UTC 存储，按会话时区显示 |
| `YEAR` | 1 字节 | 1901 到 2155 | 仅年份 |

`DATETIME` 和 `TIMESTAMP` 的关键区别：

- `TIMESTAMP` 以 UTC 存储值，并在读取时转换为会话的 `time_zone`。如果您的应用程序在多个时区运行，`TIMESTAMP` 会自动处理转换。
- `DATETIME` 存储字面值，不做时区转换——存入什么就取出什么。
- `TIMESTAMP` 有 2038 年的限制（Unix 时间戳溢出）。对于 2038 年之后的任何日期，请使用 `DATETIME`。

```sql
-- TIMESTAMP auto-updates on insert and update
created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
```

有关时区处理的完整讨论，请参阅 [MySQL 中的时间戳和时区](/zh/guides/timestamps-timezones)。

## 定点数和浮点数 {#decimal-and-floating-point}

| 类型 | 存储 | 精度 | 适用场景 |
|:-----|:--------|:----------|:---------|
| `DECIMAL(p,s)` | 可变 | 精确 | 货币、金融计算——切勿对货币使用 FLOAT |
| `FLOAT` | 4 字节 | 约 7 位有效数字 | 可接受近似值的科学数据 |
| `DOUBLE` | 8 字节 | 约 15 位有效数字 | 更高精度的近似值 |

`FLOAT` 和 `DOUBLE` 使用二进制浮点数，无法精确表示十进制小数。浮点数中的 `0.1 + 0.2` 是 `0.30000000000000004`。对于货币，请始终使用 `DECIMAL`。

```sql
-- Correct: exact decimal arithmetic
price DECIMAL(10, 2)   -- up to 99,999,999.99

-- Wrong: floating-point rounding errors will appear in financial calculations
price FLOAT
```

## JSON {#json}

`JSON` 列存储经过验证的 JSON，并提供基于路径的查询运算符。

```sql
-- Store structured data without a fixed schema
CREATE TABLE events (
    id      INT PRIMARY KEY AUTO_INCREMENT,
    payload JSON NOT NULL
);

-- Extract a field
SELECT payload->>'$.user_id' FROM events;

-- Filter on a nested field
SELECT * FROM events WHERE payload->>'$.event_type' = 'purchase';
```

`JSON` 列不能直接建索引。要为经常查询的 JSON 字段建索引，请使用生成列：

```sql
ALTER TABLE events
    ADD COLUMN event_type VARCHAR(50) AS (payload->>'$.event_type') STORED,
    ADD INDEX idx_event_type (event_type);
```

## 常见问题 {#frequently-asked-questions}

#### 主键应该用 INT 还是 BIGINT？ {#should-i-use-int-or-bigint-for-primary-keys}

`INT` 作为有符号整数可处理 21 亿行，无符号则为 43 亿行。对于大多数表，`INT UNSIGNED` 已经足够。如果您确实预计会超过这个数，或者使用的是 4 字节装不下的 UUID 风格 ID，请使用 `BIGINT`。

#### 我可以到处都用 VARCHAR(255) 来省得考虑吗？ {#can-i-use-varchar255-everywhere-to-avoid-thinking-about-it}

可以，但请声明实际的最大值：姓名字段用 `VARCHAR(100)`，而不是 `VARCHAR(255)`。无论在表中还是在 InnoDB 索引中，存储成本都与数据长度一致。声明的大小会计入 3072 字节的索引键长度限制，因此很长的 `VARCHAR` 列可能无法建立索引。

#### NULL 和默认值在实际中有什么区别？ {#whats-the-practical-difference-between-null-and-a-default-value}

`NULL` 表示"未知"——它会在表达式中传播，并被聚合函数排除。像 `0` 或 `''` 这样的默认值表示"显式设置为空"。对于确实缺失的数据选择 `NULL`；对于"尚未设置"但您希望该列立即有一个合理值的场景选择默认值。混用它们会在查询中造成不一致。

## 故障排除 {#troubleshooting}

| 问题 | 解决方案 |
|:--------|:---------|
| `Data too long for column` | 列类型太窄——增加 `VARCHAR` 长度或切换到 `TEXT` |
| 金融计算中出现舍入误差 | 把 `FLOAT`/`DOUBLE` 替换为 `DECIMAL(p,s)` |
| `TIMESTAMP` 显示的时间不对 | 会话的 `time_zone` 与预期不同——检查 `SELECT @@session.time_zone` |
| 无法在 TEXT 列上创建索引 | 使用前缀索引：`INDEX (col(100))`，或添加生成列 |
| INT 主键接近上限 | 在触及上限之前改为 `BIGINT` 或 `INT UNSIGNED` |
