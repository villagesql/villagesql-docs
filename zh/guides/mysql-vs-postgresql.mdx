MySQL 和 PostgreSQL 都是成熟的开源数据库，支撑着大规模的应用程序。两者都不是玩具，也没有哪个明显更好。它们之间的区别在于不同的默认设置、不同的社区，以及权衡在不同场景下对您有利的地方不同。本指南坦诚地梳理这些权衡，以便您为自己的项目做出决定。

## MySQL 往往胜出的地方 {#where-mysql-tends-to-win}

**运维简单性。** MySQL 的托管服务生态比 PostgreSQL 更深厚。Amazon Aurora MySQL、Google Cloud SQL for MySQL 和 Amazon RDS for MySQL 都是经过多年生产环境打磨的一流产品。如果您想运行数据库而不承担运维复杂性，MySQL 的托管选项非常出色。

**主键访问速度。** InnoDB 使用聚簇索引，这意味着行数据就存放在主键索引本身之中。一次主键查找只需一次 I/O 操作就能取到数据——不需要再去堆中取数据。对于以键为主的读取工作负载，这是一个实实在在的优势。

**极端规模下的水平扩展。** Vitess 建立在 MySQL 之上，是 YouTube、GitHub 和 Shopify 的 MySQL 部署背后的分片层。Facebook 运行 MySQL 的规模是任何类型的数据库都很少能匹敌的。如果您预计需要水平分片，MySQL 生态为此有成熟的路径。

**JSON。** MySQL 8.4 的 JSON 支持很扎实。`JSON_TABLE()` 让您可以把 JSON 数组和对象当作关系数据处理。JSONPath 运算符可以自然地用在 WHERE 子句中。您可以在 JSON 字段上创建生成列并为其建索引。人们仍然低估这一点，因为旧版 MySQL 的 JSON 支持较弱——它现在已经不弱了。

**更严格的默认设置。** MySQL 8.4 默认启用严格模式。静默数据截断、零日期插入和除以零错误都会被捕获，而不是被静默地破坏。如果您是基于 8.0 之前的数据完整性声誉来评估 MySQL，这些顾虑已经基本得到解决。

## PostgreSQL 往往胜出的地方 {#where-postgresql-tends-to-win}

**可扩展性。** 这是 PostgreSQL 最明确的结构性优势。pgvector、PostGIS、pg_partman、pg_trgm——有数百个社区扩展在数据库层面添加类型、索引方法和函数。`CREATE EXTENSION` 在 PostgreSQL 中是一等概念，围绕它的生态非常深厚。

**更丰富的原生类型。** 数组、复合类型、范围类型、hstore——PostgreSQL 有更广泛的数据建模词汇。如果您的应用程序天然地使用数组或范围，PostgreSQL 让您可以留在数据库中，而不必把一切都规范化到子表或编码为 JSON。

**标准遵循。** PostgreSQL 在边缘情况上更紧密地跟随 ANSI SQL。`RETURNING` 子句、`LISTEN`/`NOTIFY` 和对表继承的完整支持，都是在 MySQL 中不存在或工作方式不同的能力的例子。如果标准遵循是您项目的硬性要求，PostgreSQL 是更安全的选择。

**部分索引。** 您可以只为匹配某个 WHERE 子句的行建索引。当您的大部分行处于一种您很少查询的状态——比如已归档的订单或软删除的记录——时，这一点很重要。MySQL 原生没有这个功能。

**物化视图。** PostgreSQL 有原生的物化视图，您可以按需刷新。MySQL 没有；变通方法是表、存储过程和应用层编排的组合。

**全文搜索。** PostgreSQL 的 `tsvector`/`tsquery` 系统比 MySQL 的 `FULLTEXT` 索引能力更强。词干提取、排名和短语搜索在 PostgreSQL 这边都更具表达力。

## 功能对等 {#feature-parity}

如果您是因为 MySQL 旧有的声誉而避开它，其中一些差距已经弥合。

| 功能 | MySQL 8.4/9.7 | 备注 |
|:--------|:--------------|:------|
| 窗口函数 | 是 | 完整支持 |
| CTE（WITH 子句） | 是 | 包括递归 CTE |
| JSON | 是 | JSON_TABLE、JSONPath、生成列 |
| 生成列 | 是 | 存储型和虚拟型都支持 |
| CHECK 约束 | 是 | 自 8.0.16 起强制执行 |
| 不可见索引 | 是 | 在删除索引前安全地测试其移除效果 |
| 基于角色的访问控制 | 是 | |
| EXPLAIN ANALYZE | 是 | |

不可见索引值得特别指出——它们是 MySQL 独有的。您可以把一个索引标记为不可见，让优化器忽略它，验证查询计划没有退化，然后安全地删除它。PostgreSQL 没有对应的功能。

## MySQL 相对于 PostgreSQL 仍然存在的差距 {#gaps-mysql-still-has-vs-postgresql}

如果您的应用程序依赖以下任何一项，坦诚面对缺失的部分很重要：

- **没有数组列类型。** 您需要规范化到子表或编码为 JSON。
- **没有部分索引。** 常见的变通方法是一个带表达式的生成列，再在该列上建索引——可行，但不够顺手。
- **没有原生物化视图。** 您需要用表和定时存储过程自己构建。
- **没有 LISTEN/NOTIFY。** 如果您需要数据库级别的发布/订阅，您需要 MySQL 之外的一层。
- **没有表继承。** PostgreSQL 的表继承模型在 MySQL 中没有对应物。
- **扩展生态小得多。** MySQL 的插件和 UDF 系统是存在的，但与 PostgreSQL 的扩展生态相比，围绕它的社区很薄弱。

最后那个差距是大多数开发者在日常工作中真正感受到的。

## VillageSQL 在哪里弥合差距 {#where-villagesql-closes-the-gap}

扩展生态是 MySQL 和 PostgreSQL 之间最具体的结构性差异，也正是 VillageSQL 直接解决的问题。您可以像在 PostgreSQL 中运行 `CREATE EXTENSION` 一样安装网络地址类型（INET、CIDR、MACADDR）、加密函数、UUID 版本 1、3、4、5、6 和 7，以及 HTTP 客户端函数——它们是可安装的包，无需修改服务器即可直接放入使用。

扩展还可以定义带有自定义存储和比较语义的新列类型。这与 PostGIS 和 pgvector 在 PostgreSQL 中使用的能力相同，只是应用到了 MySQL 的存储引擎上。

VillageSQL 的内核仍然是 MySQL。复制、InnoDB 存储引擎、线路协议、工具生态——所有这些都保持不变。为 MySQL 构建的应用程序可以在 VillageSQL 上运行。改变的是可扩展性模型。

## 何时选择 MySQL {#when-to-choose-mysql}

- 您的团队已经熟悉 MySQL，并且没有令人信服的理由去换。
- 您部署在托管服务上，并希望使用 Aurora、Cloud SQL 或 RDS。
- 您预计需要大规模的水平分片，并希望使用 Vitess 生态。
- 您的工作负载以读为主，且以主键访问模式为主导。

## 何时选择 PostgreSQL {#when-to-choose-postgresql}

- 您需要 PostGIS 或 pgvector，并且没有可行的替代品。
- 您的应用程序以难以规范化的方式依赖数组、范围类型或复合类型。
- 标准遵循是您所处环境的硬性要求。
- 您的团队非常熟悉 PostgreSQL，并且没有迁移压力推向另一边。

## 这个决定是可逆的 {#the-decision-is-reversible}

今天在 MySQL 和 PostgreSQL 之间做选择的开发者并没有做出永久性的承诺。两个数据库都能轻松支撑大多数应用程序走到数百万用户。选择您的团队熟悉的那一个，或者您的云服务商让您最容易运维的那一个。如果您选了 MySQL，后来又希望有一个更丰富的扩展生态，那正是 [VillageSQL](https://villagesql.com/install) 旨在弥合的差距：在 MySQL 的直接替代品上提供 PostgreSQL 风格的扩展。
