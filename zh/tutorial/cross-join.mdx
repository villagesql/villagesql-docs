`CROSS JOIN` 把一个表的每一行与另一个表的每一行配对。您不写 `ON` 条件，因为没有东西需要匹配。它是您想要每一种组合时要求的连接，也是您漏掉 `ON` 子句时意外得到的连接。

开始之前，请用 `mysql -u root -p sakila` 打开客户端。

## CROSS JOIN 的工作原理 {#how-cross-join-works}

```sql
SELECT COLUMN_LIST
FROM FIRST_TABLE
CROSS JOIN SECOND_TABLE;
```

把 `COLUMN_LIST` 换成您想要的列，把 `FIRST_TABLE` 和 `SECOND_TABLE` 换成要组合的表。结果中每一种可能的配对各有 1 行，所以它的大小是第一个表的行数乘以第二个表的行数。6 行与 2 行交叉得到 12 行。

## 示例 {#examples}

### 1) 每一种组合 {#1-every-combination}

Sakila 有 6 种语言和 2 家商店。

```sql
SELECT l.name, s.store_id
FROM language AS l
CROSS JOIN store AS s
ORDER BY l.name, s.store_id;
```

```text
+----------+----------+
| name     | store_id |
+----------+----------+
| English  |        1 |
| English  |        2 |
| French   |        1 |
| French   |        2 |
| German   |        1 |
| German   |        2 |
| Italian  |        1 |
| Italian  |        2 |
| Japanese |        1 |
| Japanese |        2 |
| Mandarin |        1 |
| Mandarin |        2 |
+----------+----------+
12 rows in set (0.00 sec)
```

每种语言在每家商店各出现一次。这里没有任何东西说明某家商店有那种语言的电影存货：这些行是组合，不是关于数据的事实。这正是这个查询的目的。当您希望每一种配对都有一行，不管这个配对是否真的发生过什么时，这样的网格就是一个起始形状。

### 2) 逗号是更老的写法 {#2-the-comma-is-the-older-spelling}

```sql
SELECT l.name, s.store_id
FROM language AS l, store AS s
ORDER BY l.name, s.store_id;
```

```text
+----------+----------+
| name     | store_id |
+----------+----------+
| English  |        1 |
| English  |        2 |
| French   |        1 |
| French   |        2 |
| German   |        1 |
| German   |        2 |
| Italian  |        1 |
| Italian  |        2 |
| Japanese |        1 |
| Japanese |        2 |
| Mandarin |        1 |
| Mandarin |        2 |
+----------+----------+
12 rows in set (0.00 sec)
```

同样的 12 行。`FROM` 中 2 个表之间的逗号就是交叉连接。您会在更老的 SQL 中遇到它，匹配条件通常在下面的 `WHERE` 中，这能用，但隐藏了您正在读的是哪种连接。

逗号比 `JOIN` 绑定得更松，所以 `ON` 子句无法触及逗号另一侧的表。这 2 种写法在真实的查询中确实会一起出现，而这就是它们一起出现时出错的方式。

```sql
SELECT COUNT(*) FROM film f, language l JOIN store s ON s.store_id = f.language_id;
```

```text
ERROR 1054 (42S22): Unknown column 'f.language_id' in 'on clause'
```

当您想要交叉连接时，请写 `CROSS JOIN`，并且每个查询只用一种写法。

这个关键字也不强制执行规则。MySQL 接受 `CROSS JOIN` 上的 `ON` 子句，然后表现得像 `INNER JOIN`，所以查询中的这个词并不能证明您得到的是哪种连接。

```sql
SELECT COUNT(*) AS rows_returned
FROM film AS f CROSS JOIN language AS l ON f.language_id = l.language_id;
```

```text
+---------------+
| rows_returned |
+---------------+
|          1000 |
+---------------+
1 row in set (0.00 sec)
```

1,000 而不是 6,000：每部电影匹配到了它自己的语言。要知道一个连接做了什么，请读 `ON` 子句，而不是关键字。

## 数字会很快变大 {#the-number-gets-large-quickly}

12 行无伤大雅。对您平时查询的表做同样的操作就不是了。

```sql
SELECT f.title, l.name
FROM film AS f
CROSS JOIN language AS l
ORDER BY f.title, l.name;
```

```text
+-----------------------------+----------+
| title                       | name     |
+-----------------------------+----------+
| ACADEMY DINOSAUR            | English  |
| ACADEMY DINOSAUR            | French   |
| ACADEMY DINOSAUR            | German   |
...
+-----------------------------+----------+
6000 rows in set (0.01 sec)
```

1,000 部电影乘以 6 种语言是 6,000 行，而且每部电影现在都声称拥有全部 6 种语言。把 2 个各有 10,000 行的表交叉，答案有 1 亿行，这就是一个本该瞬间完成的查询一直跑到有人把它杀掉的原因。

MySQL 接受没有 `ON` 子句的 `INNER JOIN`，并把它当作这种连接。所以当一个连接返回大得可疑、整得可疑的数字时，漏掉的 `ON` 是第一个要检查的东西。[INNER JOIN](/zh/tutorial/inner-join) 课程展示了那种意外。

## 总结 {#summary}

- 用 `CROSS JOIN` 把一个表的每一行与另一个表的每一行配对。
- 不写 `ON` 子句，因为没有东西需要匹配。
- 预期 MySQL 仍然接受 `CROSS JOIN ... ON`，并把它当作内连接。
- 运行之前，把 2 个行数相乘来知道结果的大小。
- 把 `FROM` 中表之间的逗号读作交叉连接，并且每个查询只用 1 种写法。
- 当一个连接返回又整又大的行数时，怀疑漏掉了 `ON`。
