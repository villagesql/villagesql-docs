扩展程序可以注册自己的索引结构，并让服务器调用它。服务器拥有 SQL 语法、元数据和事务。扩展程序拥有索引的磁盘格式以及在其中的搜索过程。

有两个预览功能承载此能力。`vsql::preview::index_type` 注册索引结构本身。`vsql::preview::index_profile` 将该结构绑定到某个自定义类型，并指定索引进行计算所用的函数。两者都位于 `<villagesql/preview/index_builder.h>` 中。

<Warning>
自定义索引的 SQL 尚未实现。在所有构建版本上，任何指定自定义索引的语句都会返回 `ERROR 3219 (HY000): Extended Index feature not yet implemented`。

已实现、且仅可通过 [SQL 语法](#the-sql-syntax)中所述的测试标志从 MTR 测试套件访问的部分包括：两个功能、本页的构建器 API，以及 DDL 路径。创建索引会调用扩展程序的 `create` 钩子，并将该索引记录到服务器元数据中；删除索引会调用 `drop`；这些元数据在重启后仍然有效。

尚未实现的部分：`INSERT`、`UPDATE` 和 `DELETE` 时的索引维护，以及通过自定义索引执行查询。DML 钩子和扫描钩子从不会被调用。
</Warning>

## 三个组成部分 {#the-three-pieces}

索引类型是指结构：条目如何存储、插入、删除和扫描。每个扩展程序的每种结构注册一次，使用类似 `hnsw` 的名称。

索引函数是绑定到某个配置文件的确定性函数，例如距离函数。配置文件可绑定两类函数。使用 `with_function()` 绑定的函数在 SQL 中对用户可见，并且优化器可以为对它的调用规划索引扫描。使用 `with_helper()` 绑定的函数仅由索引实现调用。

索引配置文件将自定义类型与索引类型关联起来，并为每个绑定的函数指定一个数字 id，索引通过该 id 调用它。一个索引类型可服务于多个配置文件：`vsql_vector` 注册了单个 `hnsw` 索引类型，并在其上注册了四个配置文件——`hnsw_l1`、`hnsw_l2`、`hnsw_cosine` 和 `hnsw_inner_product`——每种距离度量对应一个。

## 注册索引类型 {#registering-an-index-type}

`make_index_type<Name, Context>()` 接受索引名称和一个按索引划分的上下文结构体，该结构体保存扩展程序所需的任何运行时状态。全部十二个钩子都是必需的，分为三组。如果缺少某个钩子，构建器将无法编译——失败的断言会指出该钩子的名称。

生命周期钩子创建索引存储、在打开表时加载索引，以及删除索引：

```cpp
bool create(Ctx *, const Index &, Space::Ref, Segment::TrxRef, char *, uint32_t);
bool load(Ctx *, const Index &, Index::StorageRef, char *, uint32_t);
bool drop(Ctx *, const Index &, Segment::TrxRef, char *, uint32_t);
```

DML 钩子在行发生变化时维护索引。删除分为两个阶段：`mark_delete` 将条目标记为已删除，或者在其 `delete_mark` 参数为 false 时取消标记，而 `purge` 则将其彻底移除：

```cpp
bool insert(Ctx *, const Index &, Segment::TrxRef,
            IndexScanKey::KeyPartData *keys, IndexScanKey::KeyPartData *pkeys,
            IndexScanKey::KeyPartRef *key_ref, char *, uint32_t);
bool mark_delete(Ctx *, const Index &, Segment::TrxRef,
                 IndexScanKey::KeyPartRef *key_ref,
                 IndexScanKey::KeyPartData *keys,
                 IndexScanKey::KeyPartData *pkeys, bool delete_mark,
                 char *, uint32_t);
bool purge(Ctx *, const Index &, Segment::TrxRef,
           IndexScanKey::KeyPartRef *key_ref, IndexScanKey::KeyPartData *keys,
           IndexScanKey::KeyPartData *pkeys, char *, uint32_t);
```

扫描钩子负责响应查询。`save` 和 `restore` 界定了一个迷你事务的边界：当服务器即将提交游标所附着的迷你事务时，会调用 `save`；在启动新的迷你事务之后，会调用 `restore`。迷你事务提交会释放页面闩锁，因此 `save` 需要记录足够的逻辑状态以便重新找到该位置，而 `restore` 需要重新获取扫描所需的各项闩锁：

```cpp
bool begin(Ctx *, const Index &, MtrCtx::Ref, const IndexScanDesc &,
           Index::Cursor *, bool *, char *, uint32_t);
bool position(Index::Cursor, Index::CursorOp, bool *, char *, uint32_t);
bool fetch(Index::Cursor, IndexScanKey::KeyPartRef *,
           IndexScanKey::KeyPartData *keys, IndexScanKey::KeyPartData *pkeys,
           char *, uint32_t);
bool save(Index::Cursor, char *, uint32_t);
bool restore(Index::Cursor, MtrCtx::Ref, bool *, char *, uint32_t);
void end(Index::Cursor *);
```

每个可能失败的钩子都以消息缓冲区及其长度作为最后两个参数，并在将消息写入其中后返回 `true` 表示失败。

游标归扩展程序所有。请在 `begin` 中分配游标并将其赋给 `*cursor`；在 `end` 中释放它并将 `*cursor` 设置为 `nullptr`。C++ SDK 不封装游标状态。

上下文不归扩展程序所有。C++ SDK 会在调用 `create` 或 `load` 之前，从 InnoDB 内存池中分配 `Index::StorageCtx<T>` 和您的 `T`，并在 `drop` 返回后销毁该内存池——这会运行 `~T`。请通过 `ctx->user()` 访问您自己的状态，通过 `ctx->arena()` 访问该内存池。切勿删除上下文、用户对象或内存池。

### 声明索引的能力 {#declaring-what-the-index-can-do}

`.capabilities()` 声明索引支持哪些访问模式。至少需要一个值。使用 `|` 组合多个值：

| 值 | 含义 |
|---|---|
| `Index::Support::POINT_LOOKUP` | 按完整键值进行精确匹配查找 |
| `Index::Support::RANGE_SCAN` | 带有起始边界、结束边界或两者的范围扫描 |
| `Index::Support::REVERSE_SCAN` | 按键的降序进行扫描 |
| `Index::Support::ORDER_BY` | 扫描按键顺序返回行，因此优化器无需排序即可满足对索引列的 `ORDER BY` |
| `Index::Support::KNN` | K 最近邻扫描，用于 `ORDER BY <distance>(<column>, <reference>) LIMIT K` |

`.storage_props()` 声明每个索引条目如何引用它所索引的数据。InnoDB 使用此项，并且必须设置 `HAS_ROW_REF` 或 `HAS_COLUMN_REF` 中的至少一个；服务器会在索引创建时选择提供哪一个：

| 值 | 含义 |
|---|---|
| `Index::Storage::HAS_ROW_REF` | 条目存储被索引行的主键，服务器通过主键查找来解析命中结果 |
| `Index::Storage::HAS_COLUMN_REF` | 条目存储服务器提供的稳定列引用，该引用在列具有稳定物理地址（例如向量列存储）时可用。这样可避免存储完整的主键 |
| `Index::Storage::REF_LOOKUP` | 索引可以根据稳定的引用令牌重新定位某个条目，当索引不支持点查找时，purge 等内部操作会使用此功能 |

声明 `REF_LOOKUP` 会带来一项义务：每个尚未被 purge 移除的条目都必须具有唯一的引用令牌，仅被标记为已删除的条目同样计入其中。扩展程序必须保证这一点。

### 索引选项 {#index-options}

DDL 中的 `WITH (M = 8, ef_construction = 64)` 会作为索引选项传递给扩展程序。服务器会先将每个键和值转为小写，因此即使 DDL 写的是 `M`，`params[i].key` 读取到的也是 `m`。请声明一个带默认值和 `parse` 函数的结构体，并使用 `.options<T, &T::parse>()` 注册它：

```cpp
struct HNSWOptions {
  int M = 16;
  int ef_construction = 200;
  static bool parse(const Index::Parameter *params, uint32_t count,
                    HNSWOptions *out, char *error_msg,
                    uint32_t error_msg_len);
};
```

请与转为小写后的键进行比较：

```cpp
if (strcmp(params[i].key, "m") == 0) out->M = atoi(params[i].value);
```

`index.options<HNSWOptions>()` 返回指向已解析结构体的指针。每个接收 `Index` 的钩子都可以访问它——生命周期钩子、DML 钩子和 `begin`。其余的扫描钩子只接收游标，因此在扫描过程中需要使用这些选项的索引类型必须在 `begin` 中将它们复制到游标中。

## 索引函数 {#index-functions}

索引函数必须是确定性的。请构建一个索引函数并将其保存在 `static const` 中——配置文件存储的是对它的引用，因此其地址必须比注册过程存活得更久：

```cpp
static const auto MY_INDEX_FN =
    make_index_function<&my_index_fn>("my_index_fn")
        .returns(vsql::REAL)
        .param(MY_TYPE)
        .param(MY_TYPE)
        .deterministic()
        .build();
```

## 索引配置文件 {#index-profiles}

配置文件指定自定义类型、索引类型，以及带有各自 id 的函数。`for_type()` 接受类型的*名称字符串*——即传给 `make_type` 的同一个常量——而不是类型描述符。`with_function()` 和 `with_helper()` 接受已构建的索引函数，而不是名称：

```cpp
static const auto MY_PROFILE =
    make_index_profile("my_profile")
        .for_type(kMyType)
        .using_index(kMyIndex)
        .with_function(1, MY_DISTANCE_FN)
        .with_helper(1, MY_HELPER_FN)
        .ordering(Index::Ordering::ASC)
        .default_for_type(true)
        .build();
```

id 在每个列表内必须唯一，且这两个列表独立编号——`with_function(1, ...)` 和 `with_helper(1, ...)` 不会冲突。同一个列表内重复的 id 会在 `INSTALL EXTENSION` 时被拒绝。

请通过 `index.profile()` 和 `index.helper()` 从钩子中调用它们：

```cpp
template <typename Result, typename... ColData>
void profile(uint32_t key_pos, uint32_t fn_id, Result *result,
             const ColData &...args) const;

template <typename Result, typename... ColData>
void helper(uint32_t key_pos, uint32_t fn_id, Result *result,
            const ColData &...args) const;
```

`key_pos` 是从零开始计数的键列，其绑定的配置文件负责分派 `fn_id`。一个配置文件附着于一个键列，因此跨多个列的索引可以通过每个位置访问不同的配置文件。`args` 中的每个值都必须是携带该列持久化形式值的 `vef_storage_col_data_t`；`static_assert` 会在编译时拒绝任何其他类型。

`.ordering()` 接受 `NONE`、`ASC`、`DESC`，或者在配置文件同时支持两种扫描方向时接受 `ASC | DESC`。如果某个距离度量的值越大表示越相似，则为 `DESC`，`vsql_vector` 正是以此方式注册 `hnsw_inner_product` 的。

`.default_for_type(true)` 将此配置文件标记为语句未指定配置文件时所使用的配置文件。它按类型和索引类型的组合生效，默认值为 false。`vsql_vector` 标记了 `hnsw_l2`，这就是为什么创建索引时未指定配置文件会记录为 `hnsw_l2`。

函数或辅助函数必须返回 `REAL`；目前不支持其他返回类型。其签名最多可声明八个参数，即 `VEF_INDEX_PROFILE_FN_MAX_ARGS` 的值。服务器会在 `INSTALL EXTENSION` 时检查这两项，而不是在首次使用时检查。

## 完整示例 {#putting-it-together}

```cpp
#include <villagesql/preview/index_builder.h>
#include <villagesql/vsql.h>

using namespace vsql::preview_index_builder;

static constexpr const char kMyType[] = "my_type";
static constexpr const char kMyIndex[] = "my_index";

constexpr auto MY_TYPE = vsql::make_type<kMyType>()/* ... */.build();

static constexpr auto MY_INDEX =
    make_index_type<kMyIndex, MyContext>()
        .lifecycle()
            .create<&my_create>()
            .load<&my_load>()
            .drop<&my_drop>()
        .dml()
            .insert<&my_insert>()
            .mark_delete<&my_mark_delete>()
            .purge<&my_purge>()
        .scan()
            .begin<&my_begin_scan>()
            .position<&my_position>()
            .fetch<&my_fetch>()
            .save<&my_save>()
            .restore<&my_restore>()
            .end<&my_end_scan>()
        .global()
            .capabilities(Index::Support::KNN)
            .storage_props(Index::Storage::HAS_COLUMN_REF |
                           Index::Storage::REF_LOOKUP)
            .options<MyOptions, &MyOptions::parse>()
            .build();

static const auto MY_PROFILE =
    make_index_profile("my_profile")
        .for_type(kMyType)
        .using_index(kMyIndex)
        .with_function(1, MY_INDEX_FN)
        .ordering(Index::Ordering::ASC)
        .default_for_type(true)
        .build();

static auto INDEX_TYPE = IndexTypeCapability().index_type(MY_INDEX);
static auto INDEX_PROFILE = IndexProfileCapability().index_profile(MY_PROFILE);

VEF_GENERATE_ENTRY_POINTS(
    vsql::make_extension()
        .with(INDEX_TYPE)
        .with(INDEX_PROFILE)
        .type(MY_TYPE))
```

两个功能对象都必须是 `static`——C++ SDK 会持有指向它们的指针——并且每个对象都必须精确地传递给 `.with()` 一次。一个功能对象可以承载多个结构：为每个结构链式调用 `.index_type()` 或 `.index_profile()`。

两次注册同一个索引类型名称，或两次注册同一个配置文件名称，都会在安装时被拒绝：

```text
ERROR HY000: Failed to install extension 'dup_index_type': index type 'DUP_INDEX' already exists
ERROR HY000: Failed to install extension 'dup_index_profile': index profile 'DUP_PROFILE' already exists
```

## SQL 语法 {#the-sql-syntax}

自定义索引通过 `USING EXTENDED` 选择，并且列可以指定要使用的配置文件：

```
INDEX <name> (<column> [[<extension>.]<profile>] [ASC | DESC])
  USING EXTENDED([<extension>.]<index_type>)
  [WITH (<option> = <value>[, ...])]
```

该子句可以内联用于 `CREATE TABLE`，也可以用于 `CREATE INDEX` 和 `ALTER TABLE ADD INDEX`。配置文件和索引类型都可以用扩展程序名称限定，您可以通过这种方式区分提供相同名称的两个扩展程序。如果未指定配置文件，服务器将使用针对该类型和索引类型声明了 `default_for_type(true)` 的配置文件。

以 `vsql_vector` 为例：

```sql
CREATE TABLE t1 (
  id INT PRIMARY KEY,
  a SVECTOR(4) NOT NULL,
  b SVECTOR(8) NOT NULL,
  INDEX idx_a (a) USING EXTENDED(hnsw),
  INDEX idx_b (b hnsw_cosine) USING EXTENDED(hnsw) WITH (M = 8, ef_construction = 64)
) ENGINE=InnoDB;

CREATE INDEX idx_c ON t1 (a hnsw_l1) USING EXTENDED(hnsw);

ALTER TABLE t1 ADD INDEX idx_d (b vsql_vector.hnsw_inner_product)
  USING EXTENDED(vsql_vector.hnsw);
```

删除自定义索引与普通索引相同：使用 `DROP INDEX`、`ALTER TABLE ... DROP INDEX`，或者 `DROP TABLE`（会随表一起移除索引元数据）。

本节中的每条语句都会返回 `ERROR 3219 (HY000): Extended Index feature not yet implemented`。

当会话设置了绕过该防护的测试标志时，调试构建版本会接受这些语句：

```sql
SET SESSION debug='+d,villagesql_custom_index_proceed';
```

自定义索引的 MTR 测试套件使用此标志。它仅运行 DDL 路径。DML 钩子和扫描钩子仍然从不会被调用，因此没有行进入索引，也没有查询从中读取。

<Note>
目前，`SHOW CREATE TABLE` 将自定义索引呈现为普通的 `KEY` 子句。索引类型、配置文件和 `WITH` 参数都不会显示，因此其输出无法还原为创建该索引的语句。
</Note>

## 元数据的存放位置 {#where-the-metadata-lives}

服务器将每个自定义索引记录在 `villagesql.custom_indexes` 中，并将其键列——以及绑定到每个键列的配置文件——记录在 `villagesql.custom_index_columns` 中。两者在重启后均保持有效。

即使以 `root` 身份，也无法从 SQL 读取这两个表：

```sql
SELECT * FROM villagesql.custom_indexes;
```

```
ERROR 3554 (HY000): Access to table 'villagesql.custom_indexes' is rejected.
```

请将它们视为服务器内部内容。目前还没有受支持的方法可以从客户端检查自定义索引元数据。
