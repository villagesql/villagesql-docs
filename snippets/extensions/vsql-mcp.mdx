`vsql_mcp` serves the database to AI agents over the Model Context Protocol,
from a listener inside the server process. An agent can list schemas, describe
tables, and run read-only queries. Writes stay off until you turn them on, and
every tool's SQL runs through a database account you nominate, so an agent is
bounded by what you granted that account.

## Install

`vsql_mcp` is not bundled with the server, so build it from the repository first
and copy the resulting `vsql_mcp.veb` into the directory named by the `veb_dir`
system variable. Then install it:

```sql
INSTALL EXTENSION vsql_mcp;
```

Confirm it is there:

```sql
SELECT EXTENSION_NAME
FROM INFORMATION_SCHEMA.EXTENSIONS
WHERE EXTENSION_NAME = 'vsql_mcp';
```

```
+----------------+
| EXTENSION_NAME |
+----------------+
| vsql_mcp       |
+----------------+
```

The build instructions are in the
[repository](https://github.com/villagesql/vsql-mcp).

## What it adds

It adds one SQL function, `info()`, which reports what the listener is doing.
Everything else is configuration and MCP traffic.

```sql
SELECT CONVERT(info() USING utf8mb4) AS info;
```

```
{"enabled":false,"http_port":0,"port":3100,"protocol_version":"2025-06-18","schema":"","sessions_active":0,"starting":false}
```

`starting` is `true` from the moment `vsql_mcp.vsql_mcp_enabled` is set `ON`
until the background worker's next wakeup, which comes every 25 ms. A call in
that window can report `"enabled":false` too, since the listener has not bound
yet.

The listener speaks two MCP revisions on the same endpoint: the stateless
revision `2026-07-28`, where each request carries its own protocol version and
stands alone, and the session-based revision `2025-06-18`, which opens a
session with `initialize`. The `info()` field `protocol_version` reports the
`2025-06-18` revision regardless of which one a client is using, and
`sessions_active` counts only `2025-06-18` sessions — a stateless request
creates none.

| Setting | Default | What it controls |
|---|---|---|
| `vsql_mcp.vsql_mcp_enabled` | `OFF` | Whether the listener runs |
| `vsql_mcp.schema` | empty | The database it serves |
| `vsql_mcp.db_url` | empty | The account every tool connects as |
| `vsql_mcp.allowed_tables` | empty | Which tables the tools may touch |
| `vsql_mcp.allow_write` | `OFF` | Whether the write tool exists at all |
| `vsql_mcp.allow_ddl` | `OFF` | Whether the ddl tool exists at all |
| `vsql_mcp.max_rows` | `1000` | The row cap on a single result |
| `vsql_mcp.query_timeout` | `30` | How long one query may run, in seconds |
| `vsql_mcp.port` | `3100` | The HTTP port |
| `vsql_mcp.require_auth` | `OFF` | Whether a request must carry a bearer token |
| `vsql_mcp.bearer_token` | empty | That token |
| `vsql_mcp.session_ttl` | `1800` | How long an idle agent session is kept, in seconds, for `2025-06-18` clients |

## Example

Point the listener at a database and start it:

```sql
SET GLOBAL vsql_mcp.schema = 'shop';
SET GLOBAL vsql_mcp.db_url = 'mysql://agent:secret@127.0.0.1:3306/shop';
SET GLOBAL vsql_mcp.allowed_tables = 'orders,customers';
SET GLOBAL vsql_mcp.vsql_mcp_enabled = ON;
```

Agents then connect to `http://127.0.0.1:3100` over MCP Streamable HTTP. The
repository carries the client configuration for each agent.

<Warning>
  The account in `db_url` sets the ceiling on what an agent can do, and every
  database account can read `db_url`, password included, with `SHOW VARIABLES`,
  so grant it the least it needs and leave `allow_write` off until you mean it.
  Turn on `require_auth` with a bearer token before the port is reachable from
  anywhere but localhost; `SHOW VARIABLES` shows that token to every account too.
</Warning>

<Note>
  A setting written with `SET PERSIST` survives a restart, but
  `UNINSTALL EXTENSION` deletes it. After an uninstall and reinstall every
  setting is back at its default, and no restart brings the old value back.
</Note>
