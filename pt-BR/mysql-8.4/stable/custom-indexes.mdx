Uma extensão pode registrar sua própria estrutura de índice e fazer com que o
servidor a chame. O servidor é dono da sintaxe SQL, dos metadados e da transação.
A extensão é dona do formato em disco do índice e da busca dentro dele.

Duas capabilities Preview sustentam isso. `vsql::preview::index_type` registra a
estrutura de índice em si. `vsql::preview::index_profile` vincula essa estrutura
a um tipo personalizado e nomeia as funções com as quais o índice calcula. Ambas
ficam em `<villagesql/preview/index_builder.h>`.

<Warning>
O SQL para índices personalizados não está implementado. Qualquer instrução que
nomeie um índice personalizado retorna `ERROR 3219 (HY000): Extended Index
feature not yet implemented` em todos os builds.

Implementados, e alcançáveis apenas a partir das suítes MTR por meio da flag de
teste descrita em [A Sintaxe SQL](#the-sql-syntax): ambas as capabilities, a API
de builder desta página e o caminho de DDL. Criar um índice chama o hook
`create` da extensão e registra o índice nos metadados do servidor; removê-lo
chama `drop`; os metadados sobrevivem a uma reinicialização.

Não implementadas: a manutenção do índice em `INSERT`, `UPDATE` e `DELETE`, e a
execução de consultas por meio de um índice personalizado. Os hooks de DML e de
scan nunca são chamados.
</Warning>

## As Três Peças {#the-three-pieces}

Um tipo de índice é a estrutura: como as entradas são armazenadas, inseridas,
excluídas e percorridas. Ele é registrado uma vez por extensão e por estrutura,
sob um nome como `hnsw`.

Uma função de índice é uma função determinística vinculada a um perfil — uma
função de distância, por exemplo. Um perfil vincula duas categorias de funções. Uma função
vinculada com `with_function()` é visível ao usuário em SQL, e o otimizador pode
planejar um scan de índice para as chamadas a ela. Uma função vinculada com
`with_helper()` é chamada apenas pela implementação do índice.

Um perfil de índice liga um tipo personalizado a um tipo de índice e dá a cada
função vinculada um id numérico pelo qual o índice a chama. Um tipo de índice
serve a muitos perfis: `vsql_vector` registra um único tipo de índice `hnsw` e
quatro perfis sobre ele — `hnsw_l1`, `hnsw_l2`, `hnsw_cosine` e
`hnsw_inner_product` — um por métrica de distância.

## Registrando um Tipo de Índice {#registering-an-index-type}

`make_index_type<Name, Context>()` recebe o nome do índice e uma struct de
contexto por índice que guarda todo o estado de execução de que a extensão
precisa. Todos os doze hooks são obrigatórios, em três grupos. O builder não
compila se um deles estiver faltando — a asserção que falha nomeia o hook.

Os hooks de ciclo de vida criam o armazenamento do índice, o carregam quando a
tabela é aberta e o removem:

```cpp
bool create(Ctx *, const Index &, Space::Ref, Segment::TrxRef, char *, uint32_t);
bool load(Ctx *, const Index &, Index::StorageRef, char *, uint32_t);
bool drop(Ctx *, const Index &, Segment::TrxRef, char *, uint32_t);
```

Os hooks de DML mantêm o índice conforme as linhas mudam. A exclusão tem duas
fases: `mark_delete` marca uma entrada como excluída, ou desfaz a marcação
quando seu argumento `delete_mark` é falso, e `purge` a remove definitivamente:

```cpp
bool insert(Ctx *, const Index &, Segment::TrxRef,
            IndexScanKey::KeyPartData *keys, IndexScanKey::KeyPartData *pkeys,
            IndexScanKey::KeyPartRef *key_ref, char *, uint32_t);
bool mark_delete(Ctx *, const Index &, Segment::TrxRef,
                 IndexScanKey::KeyPartRef *key_ref,
                 IndexScanKey::KeyPartData *keys,
                 IndexScanKey::KeyPartData *pkeys, bool delete_mark,
                 char *, uint32_t);
bool purge(Ctx *, const Index &, Segment::TrxRef,
           IndexScanKey::KeyPartRef *key_ref, IndexScanKey::KeyPartData *keys,
           IndexScanKey::KeyPartData *pkeys, char *, uint32_t);
```

Os hooks de scan respondem às consultas. `save` e `restore` delimitam uma
fronteira de mini-transação: o servidor chama `save` quando está prestes a
confirmar a mini-transação à qual o cursor está vinculado, e `restore` depois de
iniciar uma nova. O commit da mini-transação libera os latches de página, então
`save` registra estado lógico suficiente para encontrar a posição novamente e
`restore` readquire os latches de que o scan precisa:

```cpp
bool begin(Ctx *, const Index &, MtrCtx::Ref, const IndexScanDesc &,
           Index::Cursor *, bool *, char *, uint32_t);
bool position(Index::Cursor, Index::CursorOp, bool *, char *, uint32_t);
bool fetch(Index::Cursor, IndexScanKey::KeyPartRef *,
           IndexScanKey::KeyPartData *keys, IndexScanKey::KeyPartData *pkeys,
           char *, uint32_t);
bool save(Index::Cursor, char *, uint32_t);
bool restore(Index::Cursor, MtrCtx::Ref, bool *, char *, uint32_t);
void end(Index::Cursor *);
```

Todo hook que pode falhar recebe um buffer de mensagem e seu comprimento como os
dois últimos argumentos, e retorna `true` em caso de falha depois de escrever a
mensagem ali.

O cursor pertence à extensão. Aloque-o em `begin` e atribua-o a `*cursor`;
libere-o em `end` e defina `*cursor` como `nullptr`. O SDK não encapsula o estado
do cursor.

O contexto não pertence à extensão. O SDK aloca `Index::StorageCtx<T>` e o seu
`T` a partir da arena do InnoDB antes de chamar `create` ou `load`, e destrói a
arena — o que executa `~T` — depois que `drop` retorna. Alcance seu próprio
estado por meio de `ctx->user()` e a arena por meio de `ctx->arena()`. Nunca
exclua o contexto, o objeto de usuário ou a arena.

### Declarando o Que o Índice Pode Fazer {#declaring-what-the-index-can-do}

`.capabilities()` declara quais padrões de acesso o índice suporta. Pelo menos um
valor é obrigatório. Combine-os com `|`:

| Valor | Significado |
|---|---|
| `Index::Support::POINT_LOOKUP` | Busca por correspondência exata usando o valor completo da chave |
| `Index::Support::RANGE_SCAN` | Scan de intervalo com um limite inicial, um limite final, ou ambos |
| `Index::Support::REVERSE_SCAN` | Scan em ordem decrescente de chave |
| `Index::Support::ORDER_BY` | O scan retorna as linhas em ordem de chave, de modo que o otimizador pode satisfazer `ORDER BY` nas colunas do índice sem uma ordenação |
| `Index::Support::KNN` | Scan dos K vizinhos mais próximos, para `ORDER BY <distance>(<column>, <reference>) LIMIT K` |

`.storage_props()` declara como cada entrada do índice se refere de volta aos
dados que ela indexa. O InnoDB usa isso, e pelo menos um entre `HAS_ROW_REF` e
`HAS_COLUMN_REF` deve estar definido; o servidor escolhe qual deles fornecer no
momento da criação do índice:

| Valor | Significado |
|---|---|
| `Index::Storage::HAS_ROW_REF` | A entrada armazena a chave primária da linha indexada, e o servidor resolve um acerto com uma busca pela chave primária |
| `Index::Storage::HAS_COLUMN_REF` | A entrada armazena uma referência de coluna estável fornecida pelo servidor, disponível quando a coluna tem um endereço físico estável, como o armazenamento de coluna vetorial. Evita armazenar a chave primária completa |
| `Index::Storage::REF_LOOKUP` | O índice consegue relocalizar uma entrada a partir de um token de referência estável, o que operações internas como o purge usam quando o índice não tem busca pontual |

Declarar `REF_LOOKUP` traz uma obrigação: toda entrada que o purge ainda não
removeu deve ter um token de referência único, e uma entrada que está apenas
marcada como excluída também conta. A extensão precisa garantir isso.

### Opções de Índice {#index-options}

`WITH (M = 8, ef_construction = 64)` na DDL chega à extensão como opções de
índice. O servidor converte cada chave e valor para minúsculas primeiro, então
`params[i].key` vale `m` mesmo que a DDL tenha escrito `M`. Declare uma struct
com valores padrão e uma função `parse`, e registre-a com
`.options<T, &T::parse>()`:

```cpp
struct HNSWOptions {
  int M = 16;
  int ef_construction = 200;
  static bool parse(const Index::Parameter *params, uint32_t count,
                    HNSWOptions *out, char *error_msg,
                    uint32_t error_msg_len);
};
```

Compare com a chave em minúsculas:

```cpp
if (strcmp(params[i].key, "m") == 0) out->M = atoi(params[i].value);
```

`index.options<HNSWOptions>()` retorna um pointer para a struct já parseada. Ele
é alcançável a partir de todo hook que recebe o `Index` — os hooks de ciclo de
vida, os hooks de DML e `begin`. Os demais hooks de scan recebem apenas um
cursor, então um tipo de índice que precisa de suas opções durante o scan tem de
copiá-las para o cursor em `begin`.

## Funções de Índice {#index-functions}

Uma função de índice deve ser determinística. Construa uma e a mantenha em um
`static const` — o perfil armazena uma referência a ela, portanto seu endereço
tem de sobreviver ao registro:

```cpp
static const auto MY_INDEX_FN =
    make_index_function<&my_index_fn>("my_index_fn")
        .returns(vsql::REAL)
        .param(MY_TYPE)
        .param(MY_TYPE)
        .deterministic()
        .build();
```

## Perfis de Índice {#index-profiles}

Um perfil nomeia o tipo personalizado, o tipo de índice e as funções com seus
ids. `for_type()` recebe a *string com o nome do tipo* — a mesma constante
passada para `make_type` — e não o descritor do tipo. `with_function()` e
`with_helper()` recebem uma função de índice já construída, não um nome:

```cpp
static const auto MY_PROFILE =
    make_index_profile("my_profile")
        .for_type(kMyType)
        .using_index(kMyIndex)
        .with_function(1, MY_DISTANCE_FN)
        .with_helper(1, MY_HELPER_FN)
        .ordering(Index::Ordering::ASC)
        .default_for_type(true)
        .build();
```

Os ids devem ser únicos dentro de cada lista, e as duas listas são numeradas de
forma independente — `with_function(1, ...)` e `with_helper(1, ...)` não
colidem. Um id repetido dentro de uma mesma lista é rejeitado no
`INSTALL EXTENSION`.

Chame-as a partir de um hook por meio de `index.profile()` e `index.helper()`:

```cpp
template <typename Result, typename... ColData>
void profile(uint32_t key_pos, uint32_t fn_id, Result *result,
             const ColData &...args) const;

template <typename Result, typename... ColData>
void helper(uint32_t key_pos, uint32_t fn_id, Result *result,
            const ColData &...args) const;
```

`key_pos` é a coluna de chave, com base zero, cujo perfil vinculado despacha
`fn_id`. Um perfil se liga a uma única coluna de chave, então um índice sobre
várias colunas pode alcançar um perfil diferente por posição. Todo valor em
`args` deve ser um `vef_storage_col_data_t` carregando o valor da coluna em sua
forma persistida; um `static_assert` rejeita qualquer outro tipo em tempo de
compilação.

`.ordering()` recebe `NONE`, `ASC`, `DESC`, ou `ASC | DESC` quando o perfil
suporta as duas direções de scan. Uma métrica de distância em que um valor maior
significa mais similar é `DESC`, que é como o `vsql_vector` registra
`hnsw_inner_product`.

`.default_for_type(true)` marca este perfil como aquele a ser usado quando uma
instrução não nomeia nenhum perfil. Aplica-se por par de tipo e tipo de índice, e
tem o valor padrão false. O `vsql_vector` marca `hnsw_l2`, e é por isso que um
índice criado sem um perfil registra `hnsw_l2`.

Uma função ou um helper deve retornar `REAL`; nenhum outro tipo de retorno é
suportado ainda. Sua assinatura pode declarar no máximo oito parâmetros, o valor
de `VEF_INDEX_PROFILE_FN_MAX_ARGS`. O servidor verifica ambos no
`INSTALL EXTENSION`, e não no primeiro uso.

## Juntando Tudo {#putting-it-together}

```cpp
#include <villagesql/preview/index_builder.h>
#include <villagesql/vsql.h>

using namespace vsql::preview_index_builder;

static constexpr const char kMyType[] = "my_type";
static constexpr const char kMyIndex[] = "my_index";

constexpr auto MY_TYPE = vsql::make_type<kMyType>()/* ... */.build();

static constexpr auto MY_INDEX =
    make_index_type<kMyIndex, MyContext>()
        .lifecycle()
            .create<&my_create>()
            .load<&my_load>()
            .drop<&my_drop>()
        .dml()
            .insert<&my_insert>()
            .mark_delete<&my_mark_delete>()
            .purge<&my_purge>()
        .scan()
            .begin<&my_begin_scan>()
            .position<&my_position>()
            .fetch<&my_fetch>()
            .save<&my_save>()
            .restore<&my_restore>()
            .end<&my_end_scan>()
        .global()
            .capabilities(Index::Support::KNN)
            .storage_props(Index::Storage::HAS_COLUMN_REF |
                           Index::Storage::REF_LOOKUP)
            .options<MyOptions, &MyOptions::parse>()
            .build();

static const auto MY_PROFILE =
    make_index_profile("my_profile")
        .for_type(kMyType)
        .using_index(kMyIndex)
        .with_function(1, MY_INDEX_FN)
        .ordering(Index::Ordering::ASC)
        .default_for_type(true)
        .build();

static auto INDEX_TYPE = IndexTypeCapability().index_type(MY_INDEX);
static auto INDEX_PROFILE = IndexProfileCapability().index_profile(MY_PROFILE);

VEF_GENERATE_ENTRY_POINTS(
    vsql::make_extension()
        .with(INDEX_TYPE)
        .with(INDEX_PROFILE)
        .type(MY_TYPE))
```

Ambos os objetos de capability devem ser `static` — o SDK mantém pointers para
dentro deles — e cada um deve ser passado para `.with()` exatamente uma vez. Um
único objeto de capability pode carregar várias estruturas: encadeie
`.index_type()` ou `.index_profile()` por estrutura.

Registrar o mesmo nome de tipo de índice duas vezes, ou o mesmo nome de perfil
duas vezes, é recusado na instalação:

```text
ERROR HY000: Failed to install extension 'dup_index_type': index type 'DUP_INDEX' already exists
ERROR HY000: Failed to install extension 'dup_index_profile': index profile 'DUP_PROFILE' already exists
```

## A Sintaxe SQL {#the-sql-syntax}

Um índice personalizado é selecionado com `USING EXTENDED`, e a coluna pode
nomear o perfil a ser usado:

```
INDEX <name> (<column> [[<extension>.]<profile>] [ASC | DESC])
  USING EXTENDED([<extension>.]<index_type>)
  [WITH (<option> = <value>[, ...])]
```

A cláusula funciona inline em `CREATE TABLE`, e em `CREATE INDEX` e `ALTER TABLE
ADD INDEX`. Tanto o perfil quanto o tipo de índice podem ser qualificados com o
nome da extensão, que é como você desambigua duas extensões que oferecem o mesmo
nome. Quando nenhum perfil é nomeado, o servidor usa o perfil que declarou
`default_for_type(true)` para aquele par de tipo e tipo de índice.

Usando o `vsql_vector` como exemplo:

```sql
CREATE TABLE t1 (
  id INT PRIMARY KEY,
  a SVECTOR(4) NOT NULL,
  b SVECTOR(8) NOT NULL,
  INDEX idx_a (a) USING EXTENDED(hnsw),
  INDEX idx_b (b hnsw_cosine) USING EXTENDED(hnsw) WITH (M = 8, ef_construction = 64)
) ENGINE=InnoDB;

CREATE INDEX idx_c ON t1 (a hnsw_l1) USING EXTENDED(hnsw);

ALTER TABLE t1 ADD INDEX idx_d (b vsql_vector.hnsw_inner_product)
  USING EXTENDED(vsql_vector.hnsw);
```

Removê-lo é algo comum: `DROP INDEX`, `ALTER TABLE ... DROP INDEX`, ou
`DROP TABLE`, que remove os metadados do índice junto com a tabela.

Toda instrução desta seção retorna `ERROR 3219 (HY000): Extended Index feature
not yet implemented`.

Um build de debug as aceita quando a sessão define a flag de teste que contorna a
proteção:

```sql
SET SESSION debug='+d,villagesql_custom_index_proceed';
```

As suítes MTR para índices personalizados usam essa flag. Ela executa apenas o
caminho de DDL. Os hooks de DML e de scan continuam nunca sendo chamados, então
nenhuma linha chega ao índice e nenhuma consulta lê a partir dele.

<Note>
Hoje o `SHOW CREATE TABLE` mostra um índice personalizado como uma cláusula `KEY`
simples. O tipo de índice, o perfil e os parâmetros de `WITH` não são exibidos,
portanto a saída não reproduz a instrução original que o criou.
</Note>

## Onde Ficam os Metadados {#where-the-metadata-lives}

O servidor registra cada índice personalizado em `villagesql.custom_indexes`, e
suas colunas de chave — com o perfil vinculado a cada uma — em
`villagesql.custom_index_columns`. Ambos sobrevivem a uma reinicialização.

Nenhum dos dois é legível a partir do SQL, nem mesmo como `root`:

```sql
SELECT * FROM villagesql.custom_indexes;
```

```
ERROR 3554 (HY000): Access to table 'villagesql.custom_indexes' is rejected.
```

Trate-os como internos ao servidor. Ainda não há uma forma suportada de
inspecionar os metadados de índices personalizados a partir de um cliente.
