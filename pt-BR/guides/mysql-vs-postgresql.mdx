MySQL e PostgreSQL são bancos de dados maduros e de código aberto que sustentam aplicações em escala massiva. Nenhum deles é um brinquedo, e nenhum é obviamente melhor. O que eles têm são configurações padrão diferentes, comunidades diferentes e lugares diferentes em que os trade-offs pesam a seu favor. Este guia percorre esses trade-offs com honestidade para que você possa tomar a decisão para o seu projeto.

## Onde o MySQL tende a vencer {#where-mysql-tends-to-win}

**Simplicidade operacional.** O MySQL tem um ecossistema de serviços gerenciados mais profundo que o do PostgreSQL. Amazon Aurora MySQL, Google Cloud SQL para MySQL e Amazon RDS para MySQL são produtos de primeira linha com anos de amadurecimento em produção. Se você quer executar um banco de dados sem assumir a complexidade operacional, as opções gerenciadas do MySQL são excelentes.

**Velocidade de acesso por chave primária.** O InnoDB usa um índice clusterizado, o que significa que os dados da linha ficam dentro do próprio índice da chave primária. Uma busca por chave primária obtém os dados em uma única operação de I/O — não há busca no heap. Para cargas de trabalho que são principalmente leituras por chave, esta é uma vantagem significativa.

**Escala horizontal no extremo.** O Vitess foi construído sobre o MySQL e é a camada de sharding por trás das implantações MySQL do YouTube, do GitHub e da Shopify. O Facebook rodou o MySQL em uma escala que poucos bancos de dados de qualquer tipo igualaram. Se você espera precisar de sharding horizontal, o ecossistema MySQL tem caminhos bem trilhados para isso.

**JSON.** O suporte a JSON do MySQL 8.4 é sólido. `JSON_TABLE()` permite tratar arrays e objetos JSON como dados relacionais. Operadores JSONPath funcionam naturalmente em cláusulas WHERE. Você pode criar colunas geradas sobre campos JSON e indexá-las. As pessoas ainda subestimam isso porque o suporte a JSON em versões antigas do MySQL era mais fraco — ele já não é fraco.

**Configurações padrão mais rigorosas.** O MySQL 8.4 habilita o modo estrito por padrão. Truncamento silencioso de dados, inserção de datas zero e erros de divisão por zero são capturados em vez de silenciosamente mutilados. Se você está avaliando o MySQL com base em sua reputação anterior ao 8.0 em integridade de dados, essas preocupações estão em grande parte resolvidas.

## Onde o PostgreSQL tende a vencer {#where-postgresql-tends-to-win}

**Extensibilidade.** Esta é a vantagem estrutural mais clara do PostgreSQL. pgvector, PostGIS, pg_partman, pg_trgm — há centenas de extensões da comunidade que adicionam tipos, métodos de índice e funções no nível do banco de dados. `CREATE EXTENSION` é um conceito de primeira classe no PostgreSQL, e o ecossistema em torno dele é profundo.

**Tipos nativos mais ricos.** Arrays, tipos compostos, tipos de intervalo, hstore — o PostgreSQL tem um vocabulário mais amplo para modelar dados. Se sua aplicação trabalha naturalmente com arrays ou intervalos, o PostgreSQL permite que você fique no banco de dados em vez de normalizar tudo em tabelas filhas ou codificar como JSON.

**Conformidade com padrões.** O PostgreSQL segue o ANSI SQL mais de perto em casos limítrofes. A cláusula `RETURNING`, `LISTEN`/`NOTIFY` e o suporte completo a herança de tabelas são exemplos de recursos que não existem ou funcionam de forma diferente no MySQL. Se a conformidade com padrões é um requisito rígido para seu projeto, o PostgreSQL é a escolha mais segura.

**Índices parciais.** Você pode indexar apenas as linhas que correspondem a uma cláusula WHERE. Isso importa quando uma grande fração das suas linhas está em um estado que você raramente consulta — digamos, pedidos arquivados ou registros com exclusão lógica. O MySQL não tem isso nativamente.

**Views materializadas.** O PostgreSQL tem views materializadas nativas que você pode atualizar sob demanda. O MySQL não as tem; a alternativa é uma combinação de tabelas, stored procedures e orquestração no nível da aplicação.

**Busca de texto completo.** O sistema `tsvector`/`tsquery` do PostgreSQL é mais capaz que os índices `FULLTEXT` do MySQL. Stemming, ranking e busca por frase são todos mais expressivos do lado do PostgreSQL.

## Paridade de recursos {#feature-parity}

Se você evitou o MySQL com base em sua reputação antiga, algumas dessas lacunas se fecharam.

| Recurso | MySQL 8.4/9.7 | Observações |
|:--------|:--------------|:------|
| Funções de janela | Sim | Suporte completo |
| CTEs (cláusula WITH) | Sim | Incluindo CTEs recursivas |
| JSON | Sim | JSON_TABLE, JSONPath, colunas geradas |
| Colunas geradas | Sim | Tanto armazenadas quanto virtuais |
| Restrições CHECK | Sim | Aplicadas desde a 8.0.16 |
| Índices invisíveis | Sim | Teste a remoção de um índice com segurança antes de removê-lo |
| Controle de acesso baseado em papéis | Sim | |
| EXPLAIN ANALYZE | Sim | |

Os índices invisíveis merecem destaque específico — eles são exclusivos do MySQL. Você pode marcar um índice como invisível para que o otimizador o ignore, verificar que os planos de consulta não pioram e então removê-lo com segurança. O PostgreSQL não tem equivalente.

## Lacunas que o MySQL ainda tem em relação ao PostgreSQL {#gaps-mysql-still-has-vs-postgresql}

Ser honesto sobre o que falta importa se sua aplicação depende de qualquer um destes itens:

- **Sem tipo de coluna array.** Você normaliza em uma tabela filha ou codifica como JSON.
- **Sem índices parciais.** A alternativa comum é uma coluna gerada com uma expressão e então um índice nessa coluna — funcional, mas menos ergonômico.
- **Sem views materializadas nativas.** Você as constrói por conta própria com tabelas e procedures agendadas.
- **Sem LISTEN/NOTIFY.** Se você precisa de pub/sub no nível do banco de dados, vai precisar de uma camada fora do MySQL.
- **Sem herança de tabelas.** O modelo de herança de tabelas do PostgreSQL não tem equivalente no MySQL.
- **Um ecossistema de extensões muito menor.** O sistema de plugins e UDFs do MySQL existe, mas a comunidade em torno dele é rala em comparação com o ecossistema de extensões do PostgreSQL.

Essa última lacuna é a que a maioria dos desenvolvedores realmente sente no dia a dia.

## Onde o VillageSQL fecha a lacuna {#where-villagesql-closes-the-gap}

O ecossistema de extensões é a diferença estrutural mais concreta entre MySQL e PostgreSQL, e é o que o VillageSQL aborda diretamente. Você pode instalar tipos vetoriais, tipos de endereço de rede (INET, CIDR, MACADDR), funções criptográficas, UUID v1 a v7 e funções de cliente HTTP da mesma forma que executaria `CREATE EXTENSION` no PostgreSQL — como pacotes instaláveis que entram sem modificar o servidor.

As extensões também podem definir novos tipos de coluna com semântica própria de armazenamento, comparação e operadores. É a mesma capacidade que o PostGIS e o pgvector usam no PostgreSQL, aplicada ao mecanismo de armazenamento do MySQL.

O VillageSQL continua sendo MySQL por baixo. A replicação, o mecanismo de armazenamento InnoDB, o protocolo de rede, o ecossistema de ferramentas — tudo isso permanece. Aplicações construídas para o MySQL funcionam com o VillageSQL. O que muda é o modelo de extensibilidade.

## Quando escolher o MySQL {#when-to-choose-mysql}

- Sua equipe já conhece o MySQL e não há razão convincente para trocar.
- Você vai implantar em um serviço gerenciado e quer o Aurora, o Cloud SQL ou o RDS.
- Você espera precisar de sharding horizontal em escala e quer o ecossistema Vitess.
- Sua carga de trabalho é pesada em leitura, com padrões de acesso por chave primária dominando.

## Quando escolher o PostgreSQL {#when-to-choose-postgresql}

- Você precisa do PostGIS ou do pgvector e não há alternativa viável.
- Sua aplicação se apoia em arrays, tipos de intervalo ou tipos compostos de formas que seriam desajeitadas de normalizar.
- A conformidade com padrões é um requisito rígido no seu contexto.
- Sua equipe conhece bem o PostgreSQL e não há pressão de migração empurrando na outra direção.

## A decisão é reversível {#the-decision-is-reversible}

Um desenvolvedor que escolhe entre MySQL e PostgreSQL hoje não está assumindo um compromisso permanente. Ambos os bancos de dados conseguem sustentar com conforto a maioria das aplicações até milhões de usuários. Escolha o que sua equipe conhece, ou o que seu provedor de nuvem torna mais fácil de operar. Se você ficar com o MySQL e mais tarde se pegar desejando um ecossistema de extensões mais rico, essa é a lacuna que o [VillageSQL](https://villagesql.com/install) foi construído para fechar: extensões no estilo PostgreSQL em um substituto direto do MySQL.
