O modelo de controle de acesso do MySQL separa a autenticação (quem você é) da autorização (o que você pode fazer). Você cria uma conta de usuário e, em seguida, concede privilégios a ela separadamente.

## Criando Usuários {#creating-users}

```sql
CREATE USER 'alice'@'localhost' IDENTIFIED BY 'strong_password';
```

A parte `@'localhost'` é a restrição de host — esta conta só pode se conectar a partir da máquina local. Padrões de host comuns:

| Host | Significado |
|:-----|:--------|
| `'localhost'` | Conexões por socket, e conexões TCP a partir do endereço de loopback quando o servidor o resolve para `localhost` |
| `'127.0.0.1'` | Somente loopback TCP |
| `'%'` | Qualquer host (acesso pela rede) |
| `'192.168.1.%'` | Qualquer host naquela sub-rede |
| `'app.example.com'` | Nome de host específico |

`'alice'@'localhost'` e `'alice'@'%'` são duas contas distintas, embora o nome de usuário seja o mesmo.

## Concedendo Privilégios {#granting-privileges}

```sql
-- Read-only access to one database
GRANT SELECT ON myapp.* TO 'alice'@'localhost';

-- Full access to one database
GRANT ALL PRIVILEGES ON myapp.* TO 'alice'@'localhost';

-- Specific privileges on one table
GRANT SELECT, INSERT, UPDATE ON myapp.orders TO 'alice'@'localhost';

-- Global privilege (all databases)
GRANT PROCESS ON *.* TO 'alice'@'localhost';
```

O objeto do privilégio usa a notação `database.table`:
- `*.*` — todos os bancos de dados, todas as tabelas (global)
- `myapp.*` — todas as tabelas do banco de dados `myapp`
- `myapp.orders` — somente a tabela `orders`

## Níveis de Privilégio {#privilege-levels}

| Nível | Escopo | Exemplo |
|:------|:------|:--------|
| Global | Todos os bancos de dados | `GRANT RELOAD ON *.*` |
| Banco de dados | Um banco de dados | `GRANT CREATE ON myapp.*` |
| Tabela | Uma tabela | `GRANT SELECT ON myapp.users` |
| Coluna | Colunas específicas | `GRANT SELECT (id, name) ON myapp.users` |
| Rotina armazenada | Procedimento ou função | `GRANT EXECUTE ON PROCEDURE myapp.get_user` |

Privilégios comuns:

| Privilégio | O que permite |
|:----------|:---------------|
| `SELECT` | Ler linhas |
| `INSERT` | Inserir linhas |
| `UPDATE` | Modificar linhas |
| `DELETE` | Excluir linhas |
| `CREATE` | Criar tabelas e bancos de dados |
| `DROP` | Excluir tabelas e bancos de dados |
| `INDEX` | Criar e excluir índices |
| `ALTER` | Alterar a estrutura de tabelas |
| `EXECUTE` | Executar procedimentos e funções armazenados |
| `PROCESS` | Ver todas as consultas em execução (`SHOW PROCESSLIST`) |
| `SUPER` | Ignorar restrições; operações administrativas |
| `ALL PRIVILEGES` | Todos os privilégios para o escopo especificado |

## Visualizando Concessões {#viewing-grants}

```sql
-- Show grants for the current user
SHOW GRANTS;

-- Show grants for a specific user
SHOW GRANTS FOR 'alice'@'localhost';
```

## Revogando Privilégios {#revoking-privileges}

```sql
REVOKE INSERT ON myapp.* FROM 'alice'@'localhost';
REVOKE ALL PRIVILEGES ON myapp.* FROM 'alice'@'localhost';
```

Revogar um privilégio que nunca foi concedido retorna `ERROR 1141: There is no such grant defined for user`. O usuário mantém todos os privilégios concedidos em outros níveis — revogar `SELECT ON myapp.*` não remove `SELECT ON myapp.orders` se este foi concedido separadamente.

## Alterando Senhas {#changing-passwords}

```sql
ALTER USER 'alice'@'localhost' IDENTIFIED BY 'new_password';
```

Force uma troca de senha no próximo login:

```sql
ALTER USER 'alice'@'localhost' PASSWORD EXPIRE;
```

## Papéis (MySQL 8.0+) {#roles-mysql-80}

Papéis são coleções nomeadas de privilégios. Em vez de conceder privilégios individuais a cada usuário, conceda um papel.

```sql
-- Create a role
CREATE ROLE 'app_reader', 'app_writer';

-- Grant privileges to the role
GRANT SELECT ON myapp.* TO 'app_reader';
GRANT SELECT, INSERT, UPDATE, DELETE ON myapp.* TO 'app_writer';

-- Grant the role to a user
GRANT 'app_reader' TO 'alice'@'localhost';
CREATE USER 'bob'@'%' IDENTIFIED BY 'strong_password';
GRANT 'app_writer' TO 'bob'@'%';
```

Os usuários precisam ativar um papel para usar os seus privilégios (ou defini-lo como padrão):

```sql
-- Activate in session
SET ROLE 'app_reader';

-- Set default role so it activates automatically on login
SET DEFAULT ROLE 'app_reader' TO 'alice'@'localhost';
```

## Excluindo Usuários {#dropping-users}

```sql
DROP USER 'alice'@'localhost';
```

Excluir um usuário revoga automaticamente todos os seus privilégios e o remove de todos os papéis. Se o usuário estiver conectado no momento, a sessão continua até terminar.

## Boas Práticas de Privilégio Mínimo {#least-privilege-best-practices}

Dê a cada conta somente os privilégios de que ela precisa:
- Réplicas de leitura da aplicação: somente `SELECT`
- Conta de gravação da aplicação: `SELECT`, `INSERT`, `UPDATE`, `DELETE`
- Conta de esquema da aplicação (migrações): adicione `CREATE`, `ALTER`, `DROP`, `INDEX`
- Conta de DBA: `ALL PRIVILEGES` em `*.*`
- Nunca conceda `SUPER` ou `ALL` a contas de aplicação

Restrinja os hosts da forma mais rigorosa possível. Uma aplicação em `app.example.com` deve usar `'appuser'@'app.example.com'`, não `'appuser'@'%'`.

## Perguntas Frequentes {#frequently-asked-questions}

#### O MySQL recarrega as concessões automaticamente? {#does-mysql-flush-grants-automatically}

Todas as alterações feitas via `CREATE USER`, `GRANT`, `REVOKE` e `ALTER USER` têm efeito imediato — não é necessário `FLUSH PRIVILEGES`. O `FLUSH PRIVILEGES` só é necessário se você modificar as tabelas de concessão diretamente com `INSERT`/`UPDATE` (o que você não deve fazer).

#### Qual é a diferença entre `localhost` e `127.0.0.1`? {#whats-the-difference-between-localhost-and-127001}

Um cliente que se conecta a `localhost` usa o socket Unix, e o servidor registra essa conexão como host `localhost`. `127.0.0.1` é o loopback TCP. Uma conexão TCP a partir de `127.0.0.1` corresponde a uma conta `'user'@'127.0.0.1'`, e também a uma conta `'user'@'localhost'` quando o servidor resolve o endereço para `localhost`, que é o padrão.

## Solução de Problemas {#troubleshooting}

| Problema | Solução |
|:--------|:---------|
| `ERROR 1045: Access denied for user` | Senha errada, host errado ou a conta não existe — verifique com `SELECT user, host FROM mysql.user` |
| O usuário consegue se conectar, mas não consegue consultar | Verifique as concessões com `SHOW GRANTS FOR 'user'@'host'` — o nível de privilégio deve corresponder ao escopo (banco de dados vs. global) |
| `GRANT` falha com `ERROR 1044` | O usuário atual não tem o privilégio `GRANT OPTION` — conecte-se como root ou como um usuário com `GRANT OPTION` |
| Usuário criado, mas não consegue fazer login a partir do servidor da aplicação | O padrão `@'host'` não corresponde ao nome de host ou ao IP do servidor da aplicação — adicione ou atualize o padrão de host da conta |
| `DROP USER` falha | Verifique a combinação exata de usuário/host: `SELECT user, host FROM mysql.user WHERE user = 'alice'` |
